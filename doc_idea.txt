The Right Approach: ONE repo, ONE doc, with the second pipeline as an "example"
Don't split into 2 docs. That creates confusion about which to read first. The open source community expects:

ragprobe/
├── README.md              ← Landing page (hooks people in 30 seconds)
├── docs/
│   ├── quickstart.md      ← 5-minute getting started
│   ├── rag-evaluation.md  ← Deep dive: RAG scoring

│   ├── tracing.md         ← Tracing & middleware setup
│   ├── reporting.md       ← Reports + MLflow
│   └── api-reference.md   ← Full API docs
├── examples/
│   └── evaluation_framework/  ← Your 2nd pipeline lives HERE as a working example
│       ├── README.md      ← "How we tested ragprobe on a real RAG+MCP pipeline"
│       ├── ragprobe_adapter.py
│       └── ...
The second pipeline (Evaluation_Framework) becomes the example project — proving that ragprobe works on a real system. Users read the ragprobe docs, then look at the example to see it in action.

Documentation Structure
README.md — The hook. 30 seconds max to understand what ragprobe does.

# ragprobe

Pluggable evaluation for RAG pipelines and AI agents.

pip install ragprobe → plug into your RAG → get scores. No test cases to write.

[diagram showing: Your RAG → ragprobe → Scores + Reports]

## 30-Second Example

​```python
from ragprobe import RagEvaluator, DatasetGenerator, EvalAdapter

class MyRAG(EvalAdapter):
    def retrieve(self, query): return my_db.search(query)
    def generate(self, query, ctx): return my_llm(query, ctx)

dataset = DatasetGenerator(llm_fn=openai.chat).generate_from_chunks(my_chunks)
results = RagEvaluator(adapter=MyRAG()).evaluate(dataset)
print(results.summary())
​```

## What It Evaluates

| Component | Metrics | Needs Ground Truth? |
|-----------|---------|---------------------|
| Retrieval | Precision, Recall, Relevancy | No (auto-generated) |
| Generation | Faithfulness, Answer Relevancy | No |
| Agent/MCP | Tool Selection, Planning, Goal Achievement | No (LLM-as-judge) |
